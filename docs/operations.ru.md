# Обслуживание

Серверные команды выполняются от `root` или через `sudo`, из `/opt/tunnelapanel`. Если ваша установка отличается, замените пути и порты.

## Пользователи и администрирование

Изменения в разделе **Users** («Пользователи») сохраняются в черновик. Подготовьте правки, затем нажмите **Apply** («Применить»), чтобы применить их вместе, или **Discard changes** («Отменить изменения»), чтобы отменить черновик. Применение перезапускает TrustTunnel, кратковременно прерывает VPN-соединения и сбрасывает счётчики трафика. Должен оставаться хотя бы один включённый пользователь. Клиентские конфигурации, ссылки подключения и QR-коды доступны для применённых, включённых пользователей.

Ручной перезапуск VPN использует действующие настройки; черновик при этом не применяется. Перечитывание TLS-сертификата — отдельная операция. Настройте автоматическое [продление и перечитывание сертификата](https.ru.md#продление-сертификата), в том числе при доступе к панели только через SSH.

Смените начальный пароль администратора в разделе **Settings → Administrator password** («Настройки → Пароль администратора») кнопкой **Change password** («Изменить пароль»). Успешная смена пароля удаляет `runtime/panel/bootstrap-password` и завершает существующие сессии. Сессии хранятся в памяти, поэтому после перезапуска панели тоже понадобится войти снова. Пароли VPN-пользователей и пароль администратора независимы.

Для входа даётся 10 попыток на адрес клиента за 15 минут (IPv6-адреса группируются по /64), и одновременно проверяется не больше двух паролей плюс один слот, зарезервированный для адресов с успешным входом за последние 30 дней (список хранится в памяти до перезапуска панели); при массовых попытках панель отвечает, что сервер занят. `audit.jsonl` записывает отклонённые входы как `login_rate_limited` и `login_busy` — не чаще раза на адрес и окно или раза в минуту. Неудачные входы записываются не чаще 60 в минуту, остальные подсчитываются одной записью `login_failed_suppressed`. Журнал ротируется при 2 МБ и хранит пять старых копий, от `audit.jsonl.1` до `audit.jsonl.5`.

По умолчанию интерфейс отображается на английском. Выберите русский в **Settings → Interface → Language**: сохранённый выбор действует для всей панели, включая страницу входа. Сохранение не перезапускает TrustTunnel и не меняет его черновик. Подробнее — в [настройках панели](panel-settings.ru.md).

## Постоянные данные и резервные копии

| Путь | Содержимое |
| --- | --- |
| `runtime/config/` | Настройки TrustTunnel, пути TLS и действующие учётные данные VPN |
| `runtime/state/state.json` | Применённые пользователи и черновик, включая пароли отключённых пользователей |
| `runtime/state/backups/` | Учётные данные и состояние агента, сохранённые перед каждым применением; хранятся 20 последних |
| `runtime/state/apply.json` | Журнал восстановления во время применения; используется автоматически после прерванной операции |
| `runtime/panel/` | Данные авторизации администратора, начальный пароль до его смены, `settings.json` с языком интерфейса и `audit.jsonl` с пятью ротированными копиями |
| `deploy/.env`, `deploy/nginx.conf`, `deploy/certbot-deploy-hook.sh` | Параметры развёртывания и локальные правки |
| `/etc/letsencrypt/` | Сертификаты, закрытые ключи, параметры продления и установленные deploy hooks |

Оставляйте доступ к этим файлам и их резервным копиям только администратору сервера. В `runtime/` и резервных копиях применения есть пароли VPN. Храните копии вне каталога релиза и не добавляйте их в Git.

Копируйте весь каталог `runtime/`, когда административные изменения не выполняются. Сохраняйте `runtime/config/` и `runtime/state/` из одного снимка, а `runtime/panel/` включайте для сохранения данных администратора и настроек панели. Автоматические копии применения охватывают только учётные данные VPN и состояние агента; остальные пути из таблицы тоже нужно копировать. Пересоздание контейнеров сохраняет данные `runtime/`, подключённые с сервера.

## Обновление

Перед обновлением сохраните предыдущий архив релиза или присвойте рабочим Docker-образам отдельные теги. Сделайте актуальную копию постоянных данных и настроек развёртывания. Сохраните `deploy/.env` и свои правки nginx и Certbot hook: распаковка нового архива может заменить `deploy/nginx.conf` и `deploy/certbot-deploy-hook.sh`. При обновлении hook проверьте его установленную копию в `/etc/letsencrypt/renewal-hooks/deploy/`.

Соберите новые бинарники или распакуйте архив релиза по инструкции [«Установка»](installation.ru.md). Используйте существующие `.env` и `runtime/`; шаги первоначальной настройки и импорта повторять не нужно. Docker-образы используют бинарники из `dist/`; исходники Go при сборке образов не компилируются. Для обновления только панели:

```sh
docker compose -f deploy/compose.yml build panel
docker compose -f deploy/compose.yml up -d --no-deps panel
curl --fail --retry 5 --retry-connrefused --retry-delay 1 http://127.0.0.1:8080/healthz
```

Эти команды пересоздают только панель и сохраняют работающие VPN-соединения. Обновление агента или TrustTunnel также требует сборки и пересоздания `endpoint`; запланируйте краткий перерыв VPN. Перед выбором сервисов для обновления изучите изменения релиза.

### Переход на усиленную конфигурацию

Выполните этот раздел один раз, если в `deploy/.env` нет `TT_CERT_NAME`: установка сделана до версии, в которой панель работает от непривилегированного пользователя `10001`, в контейнеры монтируется только один сертификат, а панель не подключена к Docker-сети endpoint. Перед обновлением:

```sh
chown -R 10001:10001 runtime/panel
```

Добавьте в `deploy/.env` переменную `TT_CERT_NAME` с именем каталога в `/etc/letsencrypt/live/` (см. `certbot certificates`); без неё Compose не запустится. Если HTTPS-панель использует другой сертификат, задайте также `PANEL_CERT_NAME`. Проверьте, что все `cert_chain_path` и `private_key_path` в `runtime/config/hosts.toml` находятся в `/etc/letsencrypt/live/<TT_CERT_NAME>/`: иначе агент не запустится. Готовый Compose-файл монтирует для endpoint один сертификат; если нужно больше, добавьте монтирования в `deploy/compose.yml`. Переустановите [Certbot hook](https.ru.md#продление-сертификата): теперь он берёт имя сертификата из `deploy/.env`. Затем соберите и пересоздайте **все** сервисы сразу: права на сокет, нужные новой панели, создаёт агент. Запланируйте краткий перерыв VPN:

```sh
docker compose -f deploy/compose.yml build
docker compose -f deploy/compose.yml up -d
# Если установлен HTTPS-прокси:
docker compose -f deploy/compose.yml --profile https up -d https
```

После этого войдите снова. При Secure cookies имена cookie получают префикс `__Host-`.

## Диагностика

```sh
docker compose -f deploy/compose.yml ps
docker compose -f deploy/compose.yml logs --tail=100 panel endpoint
curl --fail http://127.0.0.1:8080/healthz
```

По умолчанию публичная HTTPS-панель использует порт `8443`, а VPN — публичный TCP `443`. HTTP-порт панели `8080` опубликован только на `127.0.0.1` для локальных проверок или SSH-туннеля. Успешная HTTP-проверка подтверждает, что панель отвечает; публичный HTTPS и VPN-клиент проверяются отдельно. После включения Secure cookies входите через HTTPS.

Если `endpoint` завершается с ошибкой `cannot open … from hosts.toml`, этот сертификат не входит в подключённый каталог: исправьте `TT_CERT_NAME` или путь в `hosts.toml`.

Если `panel` завершается с ошибкой `must be owned by the panel user`, выполните `chown -R 10001:10001 runtime/panel` и запустите её снова.

Если `endpoint` постоянно перезапускается, проверьте TOML-файлы, пути сертификатов и занятость публичного VPN-порта другим сервисом. Журнал самого процесса TrustTunnel доступен в разделе **Logs** («Журнал») панели. Записи журнала и диагностические сообщения endpoint сохраняют исходный язык независимо от языка интерфейса. При ошибках HTTPS-прокси проверьте также nginx:

```sh
docker compose -f deploy/compose.yml --profile https logs --tail=100 https
```

После миграции управляйте пользователями через панель. Внешние изменения `credentials.toml` блокируют применение правок, а несовпадение с сохранённым состоянием не позволяет агенту запуститься. Выясните причину внешнего изменения перед выбором снимка для восстановления.

## После перезагрузки сервера

Все сервисы используют `restart: unless-stopped`: обычно Docker запускает их после перезагрузки, кроме контейнеров, явно остановленных администратором. Проверьте все контейнеры, включая остановленные:

```sh
docker compose -f deploy/compose.yml --profile https ps -a
```

Прежний Certbot hook использовал `compose kill --signal SIGHUP`. Docker может пометить контейнер как остановленный вручную, хотя сигнал только перезагружает сертификат. Тогда endpoint и HTTPS-прокси не запускаются после перезагрузки сервера. Замените [установленный hook](https.ru.md#продление-сертификата), сохранив свой путь сертификата, затем запустите существующие остановленные контейнеры, чтобы сбросить отметку:

```sh
docker compose -f deploy/compose.yml start endpoint panel
# Если установлен HTTPS-прокси:
docker compose -f deploy/compose.yml --profile https start https
```

Команды сохраняют настройки и учётные данные; уже работающие контейнеры продолжают работу. Затем проверьте публичный HTTPS и VPN-подключение с авторизацией. Ответ самой панели ещё не подтверждает работу VPN или HTTPS-прокси.

## Восстановление конфигурации и состояния агента

Агент хранит состояние в памяти, а TrustTunnel загружает учётные данные при запуске. Для восстановления файлов нужно остановить оба сервиса; VPN-соединения прервутся:

```sh
docker compose -f deploy/compose.yml stop panel endpoint
```

Сохраните текущие каталоги для возможного отката, затем замените **оба каталога `runtime/config/` и `runtime/state/` целиком из одного согласованного снимка**, сохранив владельцев и права доступа. Не накладывайте отдельные файлы поверх существующих: оставшийся `apply.json` может перезаписать восстановленное состояние при запуске.

Автоматические файлы в `runtime/state/backups/` — JSON-записи с учётными данными и состоянием агента, а не готовые снимки каталогов для восстановления. Автоматического помощника восстановления этих записей нет.

```sh
docker compose -f deploy/compose.yml up -d --no-deps endpoint panel
docker compose -f deploy/compose.yml ps
```

Войдите снова, проверьте пользователей и состояние endpoint в панели, затем проверьте реальное VPN-подключение перед дальнейшим администрированием.

Локальные проверки и назначение smoke-теста миграции описаны в [«Разработке»](development.ru.md).
